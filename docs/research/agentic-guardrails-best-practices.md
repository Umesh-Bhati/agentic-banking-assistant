# Production agentic guardrails: evidence matrix

Research date: 2026-09-09. Scope: production LLM agents that read private data or invoke tools, with implementation notes for this repository's Mastra + Vercel AI SDK stack.

## Executive conclusion

There is no credible "perfectly aligned" or prompt-only guardrail. OWASP's latest 2026 Top 10 treats prompt injection as intrinsic to systems where instructions and data share a token stream, and OpenAI says agents can still make mistakes after applying mitigations. The defensible target is **bounded failure through defense in depth**: authenticate the user, authorize every tool call in deterministic code, minimize available functionality and privilege, isolate untrusted data, validate every boundary, require approval for consequential effects, cap resources, and continuously evaluate and monitor the whole trajectory.

The reference stack is complementary: [NIST AI RMF 1.0 and AI 600-1](https://www.nist.gov/itl/ai-risk-management-framework) for lifecycle governance, [NIST SP 800-218A](https://csrc.nist.gov/pubs/sp/800/218/a/final) with SSDF for secure AI development, and the [OWASP GenAI LLM Top 10 2026](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/) for application threats. The [OWASP Agent Control Standard](https://genai.owasp.org/resource/agent-control-standard-acs/) adds a useful agent-runtime control architecture, but it was released as a public preview on 2026-09-01 and should not yet be treated as a mature certification target. NIST also states that AI RMF 1.0 is being revised, so control mapping must be maintained as a living baseline.

Treat classifiers as one layer, not proof of safety. | OpenAI warns not to put untrusted variables in developer messages and recommends input guardrails; its safety guidance recommends adversarial tests, constrained inputs, moderation, and user identity. | Prompt injection and exfiltration | Label and isolate web/RAG/file/tool content as untrusted data, never instructions. Minimize secrets and private records in model context. Scan retrieved content and tool results, but assume detection can fail. | OpenAI recommends isolating untrusted data, structured inter-node fields, guardrails, and confirmations; it notes arbitrary text influencing tool calls raises risk. [Agent safety](https://developers.openai.com/api/docs/guides/agent-builder-safety). ## Minimum release gate

A high-stakes agent should not ship unless all of the following are demonstrated in tests and operational evidence:

1. Every tool call is authenticated, tenant-scoped, schema-validated, and authorized outside the model.
2. The model cannot directly perform a consequential mutation; a trusted, one-time approval and re-authorization boundary exists.
3. Untrusted retrieved/tool content cannot become privileged instructions or directly specify unrestricted destinations/actions.
4. Model output is inert unless it passes a typed, destination-specific validation boundary.
5. Run/tool/token/time/cost limits and idempotency protections are enforced.
6. Security, trajectory, and business-outcome evals pass for the exact model/prompt/tool configuration being deployed.
7. Sanitized traces, alerts, kill switches, rollback, and a rehearsed incident-response owner exist.
8. Memory/retention behavior is documented, tenant-isolated, deletion-capable, and verified against provider/third-party policies.

## Interpretation for this repository

The repository's documented design already appears directionally strong: authenticated request context, request-scoped aliases, private tool results, proposal-before-authorization flows, server-originated typed UI, RAG-as-untrusted-data instructions, provider allowlists, disabled-by-default mutations, and focused security tests all align with the controls above. The largest common gaps to verify before calling it production-ready are: explicit input/output processors, complete Zod output schemas on every tool, approval semantics on every consequential action, bounded agent steps/deadlines/costs, idempotency/replay protection, redacted end-to-end tracing with alerts, adversarial trajectory evals, a documented no-memory/retention posture, sandbox/egress policy, and rehearsed incident response.

“Perfect alignment” is not a valid acceptance criterion. Use measurable release thresholds, residual-risk sign-off, and continuous monitoring instead.

An architecture review alone cannot prove these controls operate correctly. Audit each one as **Fully / Partial / Missing / Not applicable**, backed by configuration/IAM evidence, test and eval results, approval traces, sanitized logs, deletion tests, incident-tabletop records, and rollback/kill-switch tests, with a named owner and remediation date for every gap.
